# Automation procedures

The scheduled tasks for this repository only say "read `docs/AUTOMATION.md` from
`main` and follow the section for your role". Change the automation by changing
this file in a reviewed PR. Background and rationale: `docs/DESIGN.md` §17, §18.

Rules for every role:

- Read everything fresh from GitHub on each run; do not rely on memory of earlier runs.
- Use the `mcp__github__*` tools (load with ToolSearch) and the
  `mcp__claude-code-remote__*` session tools. Never the `gh` CLI.
- Keep tool output small: minimal fields, `perPage` 30.
- End every GitHub comment with a blank line, `---`, then
  `_Generated by [Claude Code](https://claude.ai/code)_`.
- The user reads everything on a phone. Lead with what they must do, keep it short,
  and make every demo a tap-to-play link.

## Dispatcher (hourly)

0. **Reconcile.** For each OPEN issue labeled `in-progress`, read it
   (`issue_read`, method `get`). If `closed_by_pull_requests` contains a MERGED PR,
   close the issue (state `closed`, reason `completed`), remove `in-progress`
   (keep the other labels) and comment "Closing: PR #<n> merged to main." Merges
   by the auto-merge workflow's `GITHUB_TOKEN` do not apply closing keywords,
   which is why this step exists. For each issue still `in-progress`, find the
   worker session id in its comments and call `get_session`; if `status_bucket`
   is `failed`, relabel the issue `blocked` and comment the reason.
1. **Main CI.** List workflow runs for `main` (`actions_list`). If there are none,
   treat `main` as green. If the latest completed run is red:
   a. If no OPEN issue title starts with "Fix main", create one (labels `packet`,
   `ready`, `priority`, `tier:sonnet`, `signoff:auto`; body from
   `.github/ISSUE_TEMPLATE/work-packet.md`, "Depends on: none", the failing
   check named).
   b. If that issue is already `in-progress`, stop.
   c. Otherwise start only that issue in step 4, then go to step 5.
2. **Capacity.** Count OPEN `in-progress` issues. If 3 or more, stop. At most one
   `tier:fable` packet may be in flight.
3. **Eligible packets.** OPEN issues labeled `ready` and not `blocked`, whose
   "Depends on" issues (#n) are all CLOSED or which say "none". Order: issues
   labeled `priority` first, then lowest packet number.
4. **Start.** For each eligible issue while capacity allows: `create_session` with
   model by tier (`tier:fable` → `claude-fable-5-1`, `tier:opus` → `claude-opus-5-5`,
   `tier:sonnet` → `claude-sonnet-5-5`), `source_url`
   `https://github.com/clarktlaugh/ut-tiny`, title "P<n>: <name>" (a Fix main
   issue uses its title), tags `["ut-tiny","packet:P<n>","tier:<tier>"]`, and the
   worker prompt below with the placeholders filled. Then relabel the issue
   (remove `ready`, add `in-progress`, keep the rest) and comment
   "Started <tier> session <session id>."
5. **Report.** One short paragraph: what you closed, started and skipped, and why.
   If the GitHub or session tools are unavailable, call PushNotification once with
   the reason and stop.

### Worker prompt

```
You are a worker for GitHub issue #<issue> (packet P<n>) in clarktlaugh/ut-tiny, tier <tier>.
FIRST ACTION: call get_session with no arguments and check session_context.model matches the
tier (fable=claude-fable-5-1, opus=claude-opus-5-5, sonnet=claude-sonnet-5-5). If it differs,
comment on the issue with both values and stop.
Then read CLAUDE.md, docs/STATUS.md, the issue, the docs/DESIGN.md sections it cites, and the
"Worker" section of docs/AUTOMATION.md, and follow them. Implement the packet on branch
packet/<n>-<slug> from the latest origin/main.
```

## Worker (every packet session)

- Stay inside the issue's owned paths plus your line in `docs/STATUS.md`. Never
  change `src/sim/types.ts` or other contracts, never force-push, never merge your
  own PR.
- Run `npm run check` until green. Right before pushing, merge `origin/main` into
  your branch and re-run the check if `main` moved.
- Open the PR against `main` using `.github/pull_request_template.md`, with
  "Closes #<issue>". Subscribe with `subscribe_pr_activity` and drive it to green.
- **Green means**: the GitHub Actions jobs `check` and `owned-paths` (and
  `preview-smoke` once it exists) have run and passed on the head commit, and the
  PR has no merge conflict. Netlify's checks alone are not CI. If the jobs have
  not run, look for a merge conflict first.
- **Sign-off packets (`signoff:human`)** follow `docs/DESIGN.md` §18.8:
  - The demo is a built page on the hub, never a dev-server page.
  - Before asking for sign-off, open the deploy preview demo URL yourself and
    confirm it serves your head commit in `/version.json` and plays on an
    emulated phone and on desktop. If `preview-smoke` exists it must be green.
  - The PR description's first line is
    `▶ Play on your phone: https://deploy-preview-<PR>--tinyut.netlify.app/demos/<slug>.html`,
    then the What-to-check list, then "Merge to approve, or comment with changes."
  - Answer review comments: small, local changes go on this PR; anything larger
    becomes a new packet issue (labels `packet`, `ready`, the right tier,
    `signoff:auto`) that you link in your reply.
- **Feature packets (`signoff:auto`)** that add something visible also register
  or update a hub demo when their owned paths allow it, so the next demo packet
  can build on it.
- If CI fails three times in a row or you cannot proceed, relabel the issue
  `blocked`, comment why, and stop.
- When the PR merges, close the issue if it is still open and remove
  `in-progress`. Then stop.

## Digest (daily)

Write for a phone: under 200 words, short lines, links that open directly.

1. **Waiting on you** (first, always): every open PR whose issue is
   `signoff:human`, as "▶ <demo title>: <tap-to-play deploy preview URL>" plus
   the PR link. Also any issue labeled `blocked` and any question addressed to
   the user in an issue or PR comment from the last day. If nothing waits, say so.
2. **Merged in the last 24 hours**: PR number and title, one line each.
3. **Next up**: what the dispatcher will start next (step 3 ordering and the
   capacity limits).
4. **Cost by model** for the last day: for each `in-progress` issue and each issue
   closed in the last day, find worker session ids in its comments, call
   `get_session`, and sum `usage.cost_usd` by model. List sessions that are idle
   while their issue is still open.
5. If `docs/STATUS.md` on `main` is stale, open one small "Status refresh" PR that
   fixes only that file, and mention it.

End with the digest as your final message, then call PushNotification once with
two lines: the number of items waiting on the user, and the first demo link if
there is one.
